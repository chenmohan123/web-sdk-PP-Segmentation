# 性能与耗时

[English](../en/performance.md) · [返回 README](../../README.md)

SDK 暴露九项稳定耗时，单位均为毫秒。`sdk.loadTimings` 提供加载四项，`result.timings` 提供运行五项；这两组不是同一个计时区间。

| 字段               | 区间与解释                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `modelDownloadMs`  | 下载模型字节的耗时；本 SDK 缓存命中时为 0。浏览器 HTTP 缓存仍可能影响实际网络成本                   |
| `modelCacheReadMs` | 尝试读取 IndexedDB 的耗时，未命中也可非零                                                           |
| `integrityMs`      | 字节数及 SHA-256 校验；缓存损坏后重下载时可累计两次校验                                             |
| `sessionMs`        | runner 加载模型/ORT 与创建会话的耗时；Worker 路径包含该阶段消息交互                                 |
| `decodeMs`         | 输入读取；Blob 包括解码、方向处理、画布读像素，RGBA 包括验证和复制                                  |
| `preprocessMs`     | CPU RGB 直缩 640、量化及 NCHW 转换                                                                  |
| `inferenceMs`      | `session.run()` 的墙钟耗时；不是纯 GPU kernel 时间                                                  |
| `postprocessMs`    | 输出检查、NMS、原型组合、两次插值、裁剪和 ROI 二值打包，当前都在 CPU                                |
| `totalMs`          | 公共 `run()` 内从开始处理到返回结果的墙钟时间，含解码、调度及 Worker 传输，不含 `load()` 和 UI 绘制 |

各项存在未单列的开销，分段和不保证精确等于 `totalMs`；加载四项之和也不是整个 `load()` 的完整墙钟时间，例如缓存写入未单列。需要用户看到结果的延迟时，由应用另测加载、运行和绘制完整链路。

## 冷启动、缓存启动与热运行

- 冷启动：新实例、缓存未命中，下载、完整性校验、会话创建后首次运行。报告时同时列出加载与运行。
- 缓存启动：新实例命中版本化 IndexedDB，仍需读取、校验和创建会话；并非复用热会话。
- 热运行：同实例已完成 `load()`，串行重复 `run()` 复用会话；首次推理可能包含编译/预热开销，应单独记录预热策略。

已加载实例再次 `load()` 不重置此前 `loadTimings`。缓存命中不能仅凭总耗时推断，应结合下载为 0、缓存信息和实际加载记录判断。

React Demo 和 Vanilla 示例每图独立创建、加载并 `dispose()`，因此再次运行即使命中缓存也仍有会话创建成本。64 图 AP 基准按模式复用同一会话，其运行耗时不能直接代表 Demo 每次点击延迟。参数也不同：Demo/API 默认 `score>0.5`；AP 基准使用 `score>0.01/maxDetections=100`，可能产生更多掩码和更重后处理。

## 性能边界与调优

WebGPU 加速的是模型执行路径，当前掩码后处理仍在 CPU。主线程模式会把这部分工作放在页面线程；Worker 把预处理、推理和后处理移到 Worker，改善响应性，但输入 Blob 解码仍由调用端完成，传输和复制也有成本。Worker 不保证计算更快，GPU 推理耗时不能换算成产品 FPS。

固定模型输入为 batch 1、640×640 FP32。输入上限 16,777,216 像素，返回掩码累计上限 64 MiB；后者只约束返回字节数，不是进程峰值内存上限。大原图、多实例、临时插值缓冲、ORT 权重和张量均会占内存。

减轻开销可缩小原图、提高 `scoreThreshold` 或降低 `maxDetections`，并在业务允许时复用会话。参数改变会影响结果，比较前必须固定输入与阈值。长任务后及时 `dispose()`，不要为多张图片无限创建并发会话。
